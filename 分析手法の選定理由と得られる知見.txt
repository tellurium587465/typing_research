【全体の設計判断】なぜ統合スクリプトを 1 本にまとめ、標準ライブラリだけで書いたか
────────────────────────────────────────────────────────────────────────

■ 課題（これまでの状態）
  stats_test.py / weakness.py / trend.py / fatigue_analysis.py / arpeggio_analysis.py
  に分析が分散し、しかもセッションごとに別ファイル（jasp_trigram_<id>_clean.csv）を
  個別に処理していた。「全セッションを通した結論」を出すには毎回手作業で束ねる必要が
  あった。また numpy / pandas / scipy / matplotlib に依存しており、新しい PC や
  Python 3.14 のような新環境ではインストールが通らず分析が止まった。

■ 選択した手法と理由
  (1) キーログ・トリグラムだけで計算できる分析を 1 本（consolidated_analysis.py）に統合。
      → カメラ／MediaPipe を使う運指分析（pose 系）はデータが重く環境依存も強いので
        切り離し、「打鍵データだけで完結する層」を独立させた。最も再現性が高い部分を
        いつでも一発で回せるようにするのが目的。
  (2) 全 clean セッションを自動収集してプール（母集団を統合）してから分析。
      → 1 セッションだと N が小さく（特に S1 は 68 打鍵）統計が不安定。プールすることで
        運指パターン検定の N が数百規模になり、効果量・p 値の信頼性が上がる。
  (3) 統計関数（Mann-Whitney U / Kruskal-Wallis / Cohen's d / カイ二乗 p 値）を
      標準ライブラリ（math）だけで自前実装。
      → 「python consolidated_analysis.py」だけでどの環境でも走る。依存ゼロ＝
        将来の環境破綻に強い。研究の核心ロジックを外部ライブラリのブラックボックスに
        頼らず、検算可能な形で残す意味もある。

■ 得られること
  ・4 セッション横断の「結論」が 1 コマンドで再現できる。
  ・consolidated_report.txt（人が読むテキスト）と jasp_trigram_ALL_clean.csv
   （JASP / Excel で追検証用）の両方を同時に出力。


────────────────────────────────────────────────────────────────────────
【分析 A】セッション別トレンド ＋ セッション内疲労
────────────────────────────────────────────────────────────────────────

■ 何を計算しているか
  セッションごとに、フレーズ待機（interval > 1000ms）を除いた打鍵間隔の
  中央値・平均、ミス率、そして「疲労Δ＝後半1/3の中央間隔 − 前半1/3の中央間隔」。
  速度指標は WPM* = 60000 /（中央打鍵間隔 × 5）で表示。

■ なぜこの手法か
  ・代表値に「平均」ではなく「中央値」を主に使う：打鍵間隔は右に裾を引く分布
    （たまに長く詰まる）なので、平均は外れ値に引っ張られる。中央値の方が
    「いつもの速さ」を素直に表す。平均も併記して分布の歪みを見られるようにした。
  ・WPM ではなく「中央間隔から逆算した瞬間 WPM*」を使う：寿司打などはお題の
    待ち時間が混ざるため、生の WPM は過小評価になる。境界除外後の間隔から
    計算することで「打っている最中の純粋な速度」を出す。
  ・疲労は「前半1/3 vs 後半1/3」の差分で見る：単純な前後比較より頑健で、
    1 セッション内の集中力・手の疲れの方向（失速 / 加速）が符号で一目で分かる。

■ この分析で分かること
  ・練習を重ねて速くなっているか（セッション間の中央間隔の推移）。
  ・各セッションが「終盤に失速するタイプ」か「乗ってきて加速するタイプ」か。
    → 失速（疲労Δが大きく＋）なら 1 回の練習時間を短く区切る、加速なら
      ウォームアップを長めに取る、といった練習設計の判断材料になる。
  ・実測例: S1→S3 で中央間隔 97ms→84ms と上達。S1 のみミス率 1.5%・疲労+20ms で
    「短いセッションでまだ安定していない」状態が読み取れた。


────────────────────────────────────────────────────────────────────────
【分析 B】運指パターン別 打鍵速度の統計検定（本研究の中心）
────────────────────────────────────────────────────────────────────────

■ 何を計算しているか
  各トリグラムを「左右交互 / 同手3連 / 同指連打」に分類し、3 群の打鍵間隔を比較。
  Kruskal-Wallis 検定（3 群同時）→ Mann-Whitney U 検定（対比較）→ Cohen's d（効果量）。
  対比較の p 値は Bonferroni 補正済み。

■ なぜこの手法か
  ・ノンパラメトリック検定（Kruskal-Wallis / Mann-Whitney U）を選んだ理由：
    打鍵間隔は正規分布しない（右に裾を引く・分散が群で異なる）。t 検定や ANOVA は
    正規性・等分散を仮定するので不適。順位に基づくノンパラ検定なら分布形を仮定せず、
    外れ値にも強い。これは打鍵データの性質に対する正しい選択。
  ・Kruskal-Wallis を先に回す理由：3 群をいきなり総当たり比較すると検定回数が増えて
    偶然の有意（第一種の過誤）が膨らむ。まず「3 群のどこかに差があるか」を 1 回で
    確認し、その後で対比較に進むのが手続きとして正しい。
  ・Bonferroni 補正：対比較を 3 回行うので、有意水準をそのまま使うと誤検出が増える。
    p 値に比較回数を掛けて厳しく補正し、結論を保守的にした。
  ・Cohen's d を必ず併記する理由：p 値は「差があるか（有無）」しか言えず、N が大きいと
    些細な差でも有意になる。実務で重要なのは「差の大きさ」。d で大/中/小を示し、
    「練習で矯正する価値があるほど大きい差か」を判断できるようにした。
  ・タイ（同値）補正を自前実装に入れた理由：打鍵間隔は ms 単位で同値が多発するため、
    補正しないと検定統計量がずれる。

■ この分析で分かること
  ・運指パターンが速度に与える影響の「向き・大きさ・確からしさ」を同時に提示できる。
  ・実測結論: 左右交互 98ms ＜ 同手3連 108ms ＜ 同指連打 117ms。
    Kruskal-Wallis p=7.6e-13 で 3 群に明確な差。左右交互 vs 同指連打は d=-0.58（効果量:中）
    で +19ms 遅い。つまり「同じ指で連続して打つ配置・打ち方が最大のボトルネック」と
    統計的に裏づけられる。これが練習アプリ側の「同指連打の矯正ドリル」の根拠になっている。


────────────────────────────────────────────────────────────────────────
【分析 C】キー別 苦手スコア（カメラ不要版）
────────────────────────────────────────────────────────────────────────

■ 何を計算しているか
  キーごとに「中央遅延・CV（変動係数＝ばらつき）・ミス率」を集計し、それぞれ 0〜1 に
  正規化して合成: 苦手スコア = 0.5×遅延 + 0.3×CV + 0.2×ミス率。高いほど要練習。

■ なぜこの手法か
  ・3 要素を組み合わせる理由：単に「遅いキー」だけ見ると、たまたま難単語で 1 回詰まった
    キーが上位に来てしまう。「ばらつき（CV）」を入れることで“安定して打てていない”キーを、
    「ミス率」を入れることで“打ち間違える”キーを拾える。速い・安定・正確の 3 面で評価する。
  ・正規化してから重み付けする理由：遅延（ms）・CV（無次元）・ミス率（%）は単位が違うため、
    そのまま足せない。各指標を相対順位（0〜1）に直してから重み付けし、公平に合成する。
  ・重みを 0.5 / 0.3 / 0.2 にした理由：速度（遅延）が体感に最も直結するため最大。
    元の weakness.py（カメラ運指込み）の重み思想と、練習アプリ TypeCoach の採点に合わせた。
  ・「カメラ不要版」にした理由：本来の weakness.py は integrated.json（カメラ運指一致率・
    キー距離）を要求するが、それが無い環境でもキーログだけで苦手キーを出せるようにした。
    再現性とポータビリティのための分離。

■ この分析で分かること
  ・「今日どのキーを重点練習すべきか」が順位で出る。
  ・実測結論: 苦手 TOP5 = J, P, K, T, O。J（右人差し指、中央157ms）・P（右小指）・
    K（右中指）など右手の伸ばす/弱い指に集中。練習アプリの「苦手キー処方」は
    この上位キーを含む単語だけを出題する設計の入力になる。


────────────────────────────────────────────────────────────────────────
【分析 D】同指ビッグラム（最も遅い 2 連打の特定）
────────────────────────────────────────────────────────────────────────

■ 何を計算しているか
  連続する 2 打鍵のうち「同じ指で打つ組み合わせ（同指ビッグラム）」だけ抜き出し、
  中央間隔を全体中央値（87ms）と比較して遅い順に並べる。

■ なぜこの手法か
  ・分析 B で「同指連打が遅い」と群レベルで分かった。次に必要なのは「具体的にどの
    2 文字か」。群の結論を“練習可能な単位”に落とすため、ビッグラム粒度まで分解した。
  ・全体中央値との差（基準比）で表す理由：絶対値だけでなく「ふつうの打鍵より何 ms 余計に
    かかるか」を示すと、矯正の費用対効果が直感的に分かる。
  ・最低 N（4 回以上）でフィルタする理由：1〜2 回しか出ていない組み合わせは偶然の
    遅さを拾うだけなので除外し、繰り返し遅いものに絞る。

■ この分析で分かること
  ・矯正ドリルに入れるべき具体的な 2 文字が決まる。
  ・実測結論: AZ(+91ms), IK(+78ms), KI(+72ms), UM(+70ms), MU(+63ms) が最悪。
    特に I↔K（右中指の上下移動）と U↔M（右人差し指の上下移動）が両方向で遅い。
    → アプリの「連打→実単語」交互ドリルの出題リストに直結する。


────────────────────────────────────────────────────────────────────────
【分析 E】母音パターン別 打鍵速度（ローマ字日本語入力のリズム）
────────────────────────────────────────────────────────────────────────

■ 何を計算しているか
  トリグラムを母音/子音の並び（CVC, VCV, CCV … V=母音 C=子音）で分類し、
  パターンごとの平均・中央間隔を速い順に並べる。

■ なぜこの手法か
  ・ローマ字入力では「子音→母音→子音…」と交互に来るのが基本リズム。子音が連続する
    （CCV / CCC）と同じ手・同じ指の連続が起きやすく遅くなる、という仮説を直接検証できる
    切り口だから。日本語入力特有の構造に踏み込んだ分析。
  ・8 パターンを一覧で速度順に並べる理由：個別の単語ではなく「リズム構造」と速度の関係を
    俯瞰でき、どの構造が苦手かを一般化できる。

■ この分析で分かること
  ・日本語ローマ字入力のどの“音の並び”で失速するか。
  ・実測結論: CVV(86ms) < CVC(97ms) ≈ VCV(99ms) < … < CCV(111ms) < CCC(129ms)。
    母音を含む交互パターンは速く、子音連続（CCC）は +43ms 遅い。分析 B（同指連打が遅い）
    と整合し、「子音が固まる綴り＝物理的に指が連続して苦しい」ことを別角度から裏づける。


────────────────────────────────────────────────────────────────────────
【分析全体から導かれる一貫した結論】
────────────────────────────────────────────────────────────────────────
  3 つの独立した切り口（B: 運指パターン検定 / D: 同指ビッグラム / E: 母音パターン）が
  すべて同じ方向を指している：

      「同じ指・同じ手が連続する打鍵が最大のボトルネック」

  ・統計的に有意（B: p=7.6e-13, 効果量 中）
  ・具体的な矯正対象が特定済み（D: IK/KI/UM/MU など、C: キー J/P/K/T/O）
  ・日本語入力の構造（E: 子音連続 CCC が最遅）とも一致

  → 練習リソースは「速度の底上げ」より「同指連続の矯正」に集中投下するのが最も効率的、
    というのが本研究の中心的な実用結論。練習アプリ TypeCoach の処方ロジック
    （苦手キー処方・同指連打矯正ドリル）はこの結論を実装したもの。
