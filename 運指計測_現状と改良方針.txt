  タイピング運指の客観的データ収集 ─ 現状・目標・不足・改良点
════════════════════════════════════════════════════════════════════════
作成日: 2026-06-13

【前提】
ネット上のタイピング測定（WPM・正確率）はキーログだけで、「どの指で打ったか」
という運指(fingering)を客観的に計測するものは存在しない。本研究は
俯瞰カメラ(MediaPipe)＋打鍵音(onset)＋キーログを同期させ、運指をフレーム単位で
復元する点に新規性がある。本書はその運指計測部分を 4 観点で棚卸しする。


────────────────────────────────────────────────────────────────────────
1. 今できていること（現状）
────────────────────────────────────────────────────────────────────────
■ 3センサ同期
  ・onset_ms / pose_ms / keylog_ms を録画開始基準にそろえる
  ・カメラ実FPS(≈21.5) と設定FPS(30) のズレを meta.json / 音声長から自動補正
■ キーボード空間の復元
  ・紫バックライトを HSV 抽出 → minAreaRect で傾き取得 → 5°超でホモグラフィ補正
  ・key_positions（キー中心座標）と key_rects（実寸矩形）を生成
■ 指先追跡
  ・MediaPipe HandLandmarker で 10 指の指先を各フレームで取得（px,py,x,y,z）
  ・手の検出率 99〜100%
■ 打鍵→指の対応付け（integrate.py）
  ・打鍵ごとに onset±150ms のフレームを集め、打鍵キーに最も近い指先を「使用指」と推定
  ・標準運指(STANDARD_FINGER)と照合し finger_match / key_match を算出
  ・キー一致率 58〜84%、運指一致率 81〜91%
■ 運指の分析（integrated.json を入力）
  ・weakness.py    : キー別の苦手スコア（運指一致率・距離・ミスを合成）
  ・finger_optimize.py : 同指連打コスト・指遷移コスト行列・切り替え推奨・
                         同指ホットスポット（距離＋信頼性の二重フィルタ）
  ・stats_test.py  : 左右交互/同手/同指の打鍵速度を統計検定（→ 同指連打 +19ms 確認）


────────────────────────────────────────────────────────────────────────
2. やりたいこと（目標）
────────────────────────────────────────────────────────────────────────
  「誰でも自分のタイピングを録るだけで、
     ・各キーを実際にどの指で打っているか
     ・標準運指からどれだけ崩れているか（＝本人の癖）
     ・その崩れが速度・ミスにどう効いているか
   を、信頼できる数値で客観的に得られる」状態。

  研究としては「非標準運指が速度に与える影響」を因果に近い形で示したい。
  そのためには測定値が "本人の運指" を正しく捉えている保証（妥当性）が要る。


────────────────────────────────────────────────────────────────────────
3. 足りていないこと（不足）
────────────────────────────────────────────────────────────────────────
★ 最大の問題：「非標準運指」と「カメラ誤検出」が分離できていない
  finger_match=False のとき、それが
    (a) 本人が標準と違う指で打っている（＝計測したい本物の現象）
    (b) MediaPipe / 最近傍ロジックの誤検出（＝ノイズ）
  のどちらか区別できない。運指一致率 81〜91% の残り 9〜19% がどちらか不明では、
  「運指の癖」を客観データとして主張できない。これが研究の妥当性の根幹。

② 「キーに最も近い指＝打鍵指」という前提が弱い
  ・実際に押し下げた指ではなく、たまたまキー近くにある指を拾う恐れ
  ・単一フレームの最近傍なので、指先座標の 1 フレームのジッタに弱い
  ・押下の動き（指を伸ばして下ろす）を使っていない

③ z（深度）が完全に未使用
  pose.json は指先ごとに z を持つのに px,py 平面距離しか見ていない。
  押し下げ＝物理的に最も下がった指、という最有力の手がかりを捨てている。

④ 検出の自信度（confidence）が出力に無い
  各打鍵の推定が「ほぼ確実」か「拮抗していて怪しい」かの区別が下流に渡らない。
  finger_optimize の min-pct フィルタは集計後の事後対処で、打鍵単位の確からしさは消えている。

⑤ 妥当性検証（ground truth）の仕組みが無い
  推定運指の正解ラベルが無く、誤検出率を定量化できない。
  → 少数フレームを手ラベルして検証する手段が要る。

⑥ 右中指/右薬指の取り違え（既知）
  指の形が似て MediaPipe が混同しやすい（README既知の限界）。


────────────────────────────────────────────────────────────────────────
4. 改良点（何をどう直すか）
────────────────────────────────────────────────────────────────────────
【今回実装】打鍵→指の対応付けを「単一フレーム最近傍」から
            「多フレーム投票＋信頼度＋品質分類」へ（finger_select.py / integrate.py）

  (A) 多フレーム投票
      onset±窓 内の全フレームで、各指に
        票 = 時間の近さ × キーへの近さ（近いほど高得点）
      を加算し、合計票が最大の指を採用。単一フレームのジッタに強くなる。

  (B) 検出信頼度 confidence と 2位との差 margin を出力
      confidence = 勝者票 / 総票、margin = (勝者票−2位票)/総票。
      打鍵ごとに「どれくらい確からしいか」を数値で残す。

  (C) 品質分類で (a)非標準運指 と (b)誤検出 を分離（★最大の不足③への回答）
      ・confidence・margin が高く 標準と一致     → "standard"
      ・confidence・margin が高く 標準と不一致   → "nonstandard"（本物の癖）
      ・confidence・margin が低い                 → "uncertain"（誤検出疑い・集計から除外可）
      これで運指一致率を「高信頼サンプルのうちの標準遵守率」として正しく出せ、
      非標準運指率を本人の癖として別建てで報告できる。

  (D) サマリに品質内訳を表示
      standard / nonstandard / uncertain の件数と割合を出し、
      uncertain を除いた「妥当な運指一致率」を提示する。

【次の段階（設計のみ・本書に方針を残す）】
  ・z 深度の押下キュー：窓内で z が極小（最も下がった）瞬間の指を投票に加味。
    MediaPipe z の符号・スケールはキャリブレーションが要るので、まず
    finger_select に use_z フックを用意し（既定OFF）、検証後に有効化する。
  ・妥当性検証ツール：各セッションから N フレーム抽出し、人手で正解運指を付けて
    推定と突き合わせ、誤検出率・取り違え行列（特に R3↔R2）を出す validate_finger.py。
  ・右中指/右薬指の事前分離：手のランドマーク全体（指の付け根の並び）から
    指IDを幾何学的に補正してから投票に渡す。


────────────────────────────────────────────────────────────────────────
5. この改良で得られること
────────────────────────────────────────────────────────────────────────
  ・「運指一致率が低い」を “癖” と “ノイズ” に切り分けられ、研究主張の妥当性が出る。
  ・打鍵ごとの confidence により、下流分析（weakness/finger_optimize/stats_test）が
    高信頼サンプルだけで再計算でき、結論のロバスト性が上がる。
  ・nonstandard と判定された打鍵だけ集めれば「本人の運指の癖カタログ」が作れる
    （どのキーをどの指で代用しているか）。これは既存ツールに存在しない出力。


────────────────────────────────────────────────────────────────────────
